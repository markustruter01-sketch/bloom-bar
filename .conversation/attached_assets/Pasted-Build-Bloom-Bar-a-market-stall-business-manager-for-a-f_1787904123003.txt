PHASE 1 — AUTOMATED FLOWER DATA ENRICHMENT (THE CRITICAL FEATURE)
=====================================================================

The owner must NEVER have to type care instructions, vase life, toxicity or
conditioning notes by hand. The system researches every flower online and fills
the library itself. Accuracy is the hard requirement — a confidently wrong pet
safety answer is worse than a blank field.

Build a backend enrichment service. Given a flower's common_name it:

STEP 1 — Resolve identity.
  Call the Anthropic API (model claude-sonnet-4-6) with the web_search tool
  enabled to establish the correct botanical name and confirm the common name
  refers to a cut flower used in floristry. If the name is ambiguous (e.g.
  "Gum" could be several Eucalyptus species), return candidate options for the
  user to pick from rather than guessing. All later research uses the resolved
  botanical name.

STEP 2 — Research each field group in a SEPARATE API call with web_search on.
  Separate calls keep each search focused and improve source quality:
   a) Vase life & conditioning (fresh, fresh with flower food, dried)
   b) Handling flags: ethylene sensitivity, ethylene production, sun
      sensitivity, water uptake, whether buds open further after purchase
   c) Toxicity and pet safety
   d) Fragrance, typical colours, typical stem length, symbolic meaning
   e) Seasonality in South East Queensland, Australia (southern hemisphere —
      do NOT accept northern hemisphere seasonality)
   f) Drying suitability and method

STEP 3 — Return strict JSON only, no prose, no markdown fences. For EVERY field:
  { "field_name": {
      "value": <value or null>,
      "confidence": "high" | "medium" | "low" | "not_found",
      "source_url": "<url>",
      "source_title": "<title>",
      "raw_evidence": "<the sentence from the source supporting this value>"
  } }

ACCURACY RULES — enforce these in the system prompt of every call:
  - NEVER infer, estimate, or fill a value from general knowledge. If web
    search does not surface a supporting source, return null with
    confidence "not_found". A blank field is a correct answer.
  - Every non-null value must have a real source_url that appeared in search
    results and a raw_evidence sentence from that source. No source, no value.
  - Prefer in this order: university agricultural extension services (.edu),
    government agriculture departments (.gov / .gov.au), ASPCA, RSPCA,
    peer-reviewed horticultural literature, established commercial florist
    wholesalers. Rank blogs and retail marketing pages lowest and mark
    anything sourced only from them as confidence "low".
  - Vase life must be corroborated by TWO independent sources. If they agree,
    confidence "high". If they disagree by more than 3 days, store the wider
    range and set confidence "medium". One source only = "low".
  - PET SAFETY IS SAFETY-CRITICAL. Only accept "safe" or "toxic" from ASPCA,
    RSPCA, a veterinary body, or a government source. Anything else, or no
    source, sets pet_safe = "unverified". NEVER default to "safe". Absence
    of evidence of toxicity is not evidence of safety.
  - Seasonality must come from an Australian or southern-hemisphere source.
    If only northern hemisphere data is found, return not_found rather than
    inverting the months yourself.
  - conditioning_notes are practical instructions for the owner (how to cut,
    hydrate, what temperature). customer_care_notes are max 2 short sentences
    a buyer can follow at home. Do not mix them.

STEP 4 — Write results to flowers and one flower_field_sources row per field.
  Set enrichment_status = 'complete' if every field is high or medium,
  otherwise 'needs_review'.

PAIRING ENRICHMENT — a separate routine.
  For each pair of flowers in the library, research shared-vase compatibility
  with web_search. Store rule + reason + source_url in flower_pairings.
  Pre-seed known hard rules and still cite them:
   - Narcissus and Daffodil: 'avoid' with all other flowers — their sap
     shortens companion vase life in shared water.
   - Any flower with ethylene_producer = true: 'caution' against any flower
     with ethylene_sensitive = true.
  Only mark a pair 'safe' when a source supports it; otherwise leave it
  unrated rather than assuming safe.

UI:
- "Enrich" button on each flower. "Enrich all" bulk action on the library index
  with a progress indicator, run as a background job with rate limiting so it
  doesn't hammer the API.
- Every field in the flower detail form shows a small coloured dot (green high,
  amber medium, red low, grey not found) and a link to its source. Hovering or
  tapping the dot shows the raw_evidence sentence.
- A REVIEW QUEUE screen listing only fields with confidence low or not_found,

  than all of it. Confirming a field sets user_verified = true and locks it

- "Re-enrich" never overwrites a user_verified field.

Markets index: each market date with spend, revenue, margin. "New market"

Purchase entry (/markets/:id/buy):
- Upload or camera-capture a receipt photo.
- POST as base64 to the Anthropic API (claude-sonnet-4-6) with a prompt

  { flower_name, qty_stems, price_per_stem, line_total, confidence }.
  If a line is priced per bunch, also extract stems_per_bunch and divide.
- Fuzzy-match extracted names to the library. Review table with editable
  dropdowns, per-row confidence, and an "add as new flower" action that
  immediately triggers Phase 1 enrichment for that new flower.
- NOTHING commits until Confirm is pressed.
- Manual entry path alongside OCR for when there's no receipt.

Buy list (/markets/:id/list): mobile-first, huge text, high contrast, offline.

Running spend total against a budget the owner sets.

Pack-down (/markets/:id/close): one row per flower, two number inputs —
stems taken, stems returned. Computes sell-through %. Big touch targets,
works offline, syncs later.

Price history: per-flower chart of wholesale $/stem over time, plus a
library-wide view of which flowers are trending up or down in cost.

=====================================================================
PHASE 5 — BOUQUET GENERATOR
=====================================================================

/markets/:id/bouquets — generate bouquet suggestions from the stems actually
purchased for that market. This is NOT random combination.

1. STRUCTURE. Each bouquet follows a recipe shape:
   Petite ($25-30):  1 focal, 2 secondary, 3 textural, 2 filler, 3 foliage
   Standard ($35-40): 2 focal, 3 secondary, 4 textural, 3 filler, 4 foliage
   Lush ($45-50):    3 focal, 4 secondary, 5 textural, 4 filler, 5 foliage
   Allow +/-1 stem per role to hit the price target.
2. PRICE FIT. Sum of (stem count x band retail price) must land within $2 of
   the target. Generate for $25, $30, $35, $40, $45, $50.
3. PAIRING CONSTRAINT. Reject any combination containing a pair marked
   'avoid'. Warn on 'caution'. Treat unrated pairs as allowed but note it.
4. STOCK CONSTRAINT. Maintain a running pool of available stems across ALL
   generated bouquets for the market — never propose six bouquets that each
   need the same 3 protea stems. Show remaining unallocated stems.
5. VASE LIFE COHERENCE. Warn if the shortest-lived flower has less than 60%
   the vase life of the longest — the bouquet will look half-dead early.
6. COLOUR. Use typical_colours to avoid clashes; prefer 2-3 colour bouquets.

Output: card per bouquet — stem list, total retail, total wholesale cost,
margin %, vase life estimate, warnings. Buttons: Regenerate, Lock, Mark built.
Locking removes those stems from the available pool.
